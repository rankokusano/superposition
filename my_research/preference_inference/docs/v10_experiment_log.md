## 1. 背景の要約（指示書 §1）

- 元論文（Noguchi et al., 2022）：A-1 が一人称視覚と自分の運動から次の視覚を予測。共有 LSTM（Superposition Module）を自己（process-1）と他者（process-2）で重み共有・記憶別で使い、自他の位置・他者の視点・他者の運動を予測学習だけで獲得した。
- 本研究 v4〜v7：入力を運動から行動価値（8方向の probe-Q）に置き換えた。v4 で自己位置は保たれた（R3-A_400、h¹→自己 0.906）が、他者の価値は生成できない。v5（Encoder 再学習）は他者表現が弱まる。v6（報酬推定）は推定がほぼ定数。v7（逆強化学習）は目標は当たるが状態を壊しても当たり、行動の向きだけで決まっていた。
- 指導教員の指摘（v10 の出発点）：今のモデルでは**価値が位置に結びついている**。まず**価値と色が結びつく**かを確かめる。自他の区別は位置で成り立ち、価値を使っている証拠にならない。他者の価値の推定はいったん止める。**赤と緑の位置だけを入れ替える**。
- これまでの結果との対応：A-1 はランダムに歩くので、Q値は「今どこにいるか」の手がかりにしかならない。v7 では critic の最良方向が場所によらずほぼ一定（赤で 129°）。四隅の配置では「赤の方へ」と「左上の方へ」が区別されない。v4 の critic_swap（−34.8%）の根拠となった「価値の構造」自体が位置で決まっている可能性がある。

## 2. v10 の問いと主張（指示書 §2）

- **問い**：価値は「色」に結びついているか、「場所」に結びついているか。入れ替えのある環境で学習すれば、色に結びつくか。
- **段階A**：既存のモデルでは価値が場所／色のどちらに結びついていたかを、どちらの結果でもそのまま記録する。
- **段階B（成功した場合）**：入れ替えのある環境で学習すると、critic の価値と、共有モジュールの自己の内部状態が、場所ではなく色に沿って整理される。
- **限界（必ず明記）**：critic は共有モジュールの外の別ネットワークで、強化学習で学習している。段階Bで価値が色に結びつくかは主に critic の学習で決まり、報酬が色で定義されている以上ある程度予想どおり。共有モジュールについて言えるのは「色に結びついた価値を渡されたとき、内部状態も色に沿って整理されるか」まで。
- **主張しない**：「価値と行動が結びついた」「他者の価値が分かった」。
- **やらない**：他者の価値の推定（VE・逆強化学習）、A-1 の動き方の変更（ランダム歩行のまま）、critic を外す・入力を運動に戻すなどの構成変更（v11）。v8・v9 の構想は使わない。

### 2.1 指導教員の提案による設定変更（指示書 §4.1）

- 赤と緑の位置を入れ替える。入れ替え後は 赤 (−9,−9)、緑 (−9,9)。青・シアンはそのまま。
- 段階Bでは、エピソードごとに 1/2 の確率で入れ替える。
- 変えないもの：色・報酬関数・視覚の解像度・行動空間・エピソード長・青とシアンの位置・A-1 の動き方と好み（A-1 赤、A-2 緑、単一）。

## 4. シミュレータ調査（§6.0 の調査。コード変更なし、2026-10-15）

調べたファイル：root の `simulation/simulation/{world.py, camera.py, common_world.py, objloader.py, geometry/model.py, shader/color_*.glsl}`、`simulation/simulation/resource/model/field.{obj,mtl}`、`simulation/{creator,environment}.py`。PI の `simulation/` は root の写し（`diff -rq` で内部パッケージは同一。PI 側の追加は収集・学習スクリプトのみ）。読み取り専用の描画テストを1本、コンテナ内で実行（スクリプトは標準入力から流し、ファイルは書いていない）。

### 4.1 ランドマークの定義

- **フィールドのメッシュ `field.obj` に含まれている**（コードでの配置ではない）。6×6×6 の立方体が4つ、アリーナ（±10）の**外側**の四隅に置かれている（各軸 10〜16、中心 ±13）。色は `field.mtl` のマテリアル（`Kd`）で指定。
- **色の名前の対応に注意**：`Camera.read_pixel()` が `GL_BGR` で読むため、配列のチャンネル 0 にはマテリアルの青成分が入る。プロジェクトで「赤」と呼んでいるもの（チャンネル0）は、`field.mtl` では **`blue` マテリアル**の立方体（`Cube.001`、世界座標 x∈[−16,−10]、z∈[10,16]）。「緑」は `green` マテリアル（`Cube.002`、x,z∈[−16,−10]）。「青」は `red` マテリアル（`Cube`）。「シアン」は `yellow` マテリアル（0.8,0.8,0 → BGR で 0,0.8,0.8）。
- 世界座標とアリーナ座標：`World.draw` が `set_xz(p[0], p[1])` を呼ぶので、エージェント位置 p=(x,y) は世界の (x, z)。
- 描画テストで確認：A-1 を (−9,9) に置くと赤の割合 0.0938、(−9,−9) で緑 0.0938、(9,−9) で青、(9,9) でシアン（他者は (50,50) に退避）。プロジェクトの記述（赤 (−9,9) など）と一致。
- **プロジェクトの座標 (±9,±9) は立方体の中心ではない**（立方体の中心は (±13,±13)、近い角は (±10,±10)）。v6/v7 の解析（`actor_rollout_v7.py` など）は (±9,±9) を基準にしている。v10 では指示書どおり (±9,±9) を基準にする（§5.0 の登録）。

### 4.2 全方位の視界の列の向き

- **世界の方角に固定**。`World.draw` は毎フレーム `set_degree(-ANGLE_OFFSET)`（=−90°、定数）を設定し、エージェントの向きは描画に使われない。8台のカメラ（各 45°）の方角も固定。
- 描画テストで確認：赤の画素は A-1 の位置によらず列 49〜62、緑は列 1〜14 の範囲（位置で数列ずれるだけ）。
- **入れ替えの解釈**：入れ替え後は、赤が視界の「緑があった列の範囲」に、緑が「赤があった列の範囲」に現れる。青・シアンの列は変わらない。

### 4.3 光源と色の判定

- シェーダは光源を視点座標 (0,0,2) に置き、色 = (0.7 + ランバート)·Kd + 鏡面·Ks。Ks は灰色 (0.5,0.5,0.5)。どれもチャンネルごとに線形で、赤・緑のマテリアルは「1チャンネルだけ 0.8」の同じ形なので、**同じ立方体の色を入れ替えれば、判定（該当チャンネル > 0.9、他 < 0.1）に通る画素の集合はそのまま入れ替わる**と予想される（関門 6.0 で実測）。
- 鏡映対称の再確認：7×7 格子で |緑(x,y) − 赤(x,−y)| の最大 = **0.0**（v4 の観察と一致）。

### 4.4 入れ替えの実装方法（案。草野さんの確認後に実装）

- 方法：**マテリアルの差し替え**。`field.obj` のコピー `field_swap_rg.obj` を作り、`Cube.001` と `Cube.002` の `usemtl` 行（`blue` ↔ `green`）だけを入れ替える。立方体の位置・大きさ・光源・他の色は変えない。
- エピソードごとの切り替え：v10 用のシミュレータのコピーで、`World.init()` が両方のフィールドを読み込み、`World.set_layout('original' | 'swap_rg')` で片方だけを `visible` にする。見えない物体は描画されないので、`original` では従来と同じ描画命令列になる見込み（bit-identical は関門 6.0 で確認）。切り替えは GL の再初期化を伴わないので、エピソードの境目で呼べる。
- 配置の設定は1か所（新しいモジュール `sim_v10/layout.py`：配置名 → フィールドのファイル名・各色の基準位置 (±9,±9)・立方体の中心）。スクリプトからは `env.set_layout(name)` で呼ぶ。
- 名前の衝突を避けるため、コピーは別名のパッケージ `my_research/preference_inference/sim_v10/` にし、内部の import を相対 import にする（root の `simulation` パッケージと同時に読み込まれても衝突しない）。
- 既存のシミュレータ（root・PI の `simulation/`）・`field.obj`・既存の収集スクリプトには一切書き込まない。

### 5.8 設計判断とその理由

- **基準位置を (±9,±9) にする**：指示書の定義どおり、かつ v6/v7 の解析と同じ。立方体の中心 (±13,±13) との差は §4.1 に記録し、参考値として併記する。
- **入れ替えをマテリアルの差し替えで行う**：位置・形・光源をまったく変えずに色だけを交換でき、変える量が最小になる。描画テストで、色の判定がチャンネルごとに線形であることを確認している（§4.3）。
- **視界の列は世界の方角に固定されている（エージェントは回転しない）。ランドマークの立方体はアリーナの外（中心 (±13,±13)、各軸 10〜16）にある**（§4.1・§4.2）。このため、アリーナのどこにいても各ランドマークはほぼ同じ方角・同じ列の範囲に見える（例：元の配置で赤は常に列 49〜62）。これは、v7 で critic の最良方向が場所によらずほぼ一定だった（r=赤で 97.6〜100% のフレームが 129°）ことの説明候補である：critic は「赤い画素がどの列にあるか」ではなく「北西の列に何かがある」ことに、あるいは色に関係なく固定の方角に反応しているだけかもしれない。**元の配置では「色を見ている」と「列（方角）を見ている」が区別できない。** 入れ替えでは赤が「元は緑が見えていた列の範囲」に移り、青・シアンの列は変わらないので、**critic が色を見ているか、列（方角）を見ているかを切り分けられる。** これが v10 の入れ替えの意義である。
- **プロジェクトの「赤」は、`field.mtl` では `blue` マテリアル（`Cube.001`）である**。`Camera.read_pixel()` が `GL_BGR` で読むため、配列のチャンネル 0 にマテリアルの青成分が入る。同様に「青」は `red` マテリアル（`Cube`）、「シアン」は `yellow` マテリアル、「緑」は `green` マテリアル（`Cube.002`）。入れ替えでは `Cube.001`（blue マテリアル＝赤）と `Cube.002`（green マテリアル＝緑）の `usemtl` を交換する。コードやメッシュを読むときに名前を取り違えないこと。

**判定（事前登録の規則、§5.2）：A-1 の critic は「場所に結びついている」。** 入れ替え環境で、最良方向（K=64）と赤の方向の角度差の平均 110.9°、元の赤の場所 (−9,9) の方向との角度差の平均 26.5°（差 84°、基準 15°）。K=8、立方体の中心を基準にした場合、A-1 の actor でも同じ。A-2 の critic・actor も同じ規則で「場所」（critic 104.9° vs 31.6°）。

**観察**
1. **critic は入れ替えにほとんど反応しない。** 同じ格子点での最良方向の変化は平均 1.5°（A-1）、Q(s, a_probe) の両配置間の相関 0.996。Q 値マップの最大位置も両配置で同じ (−8,10)（入れ替え後は緑のそば）。A-1 の critic は、赤・緑のどちらが見えているかではなく、見えている景色の配置（どの列に何かがあるか、床や空の形）で価値を決めていると読める。元の配置の学習データでは色と方角が完全に一致していたので、色を見る必要がなかった。
2. **A-2 の actor は元の緑の場所へ行く。** 入れ替え後も 3000 エピソードすべてで終端は左下（今は赤）から 5 以内、左上（今の緑）から 5 以内は 0。対にしたエピソードの軌道の差は平均 0.42。§1.4 の「色ではなく場所で動いている」がそのまま当てはまる。
3. **共有モジュールの入力が、入れ替えでほとんど変わらない（事前登録外の探索的な確認、`v10_results_log.md` §3.5。§5.14 参照）。** probe-Q から配置はほぼ読めない（0.524、chance 0.5）。元論文の凍結 Encoder の自己側出力 sv_enc は、対のフレームの距離が通常のフレーム間の距離の 12% しか変わらない（ただし線形には 0.879 で読める＝小さな色の差は残っている）。その結果、h¹→自己は入れ替え後もほぼ保たれる（A0 0.9065 → A1 0.8938、A0 の回帰器のままでも 0.8896）。**h¹ の自己位置の表現は、色ではなく場所で決まる入力から作られている。**
4. **予測画像では、入れ替え後も元の配色が描かれる。** R3-A_400 も v5_base_l1 も、自己の予測で赤を右側（元の赤の列）、緑を左側に描く。Autoencoder（Fig.5 の経路）の自己再構成も、現在のフレームを入力しているのに同じく元の配色で描く（入力の赤は左 0.055 / 右 0.000、再構成の赤は左 0.000 / 右 0.062）。**Encoder→Decoder の経路が、赤・緑の区別をほとんど保たず、列の位置から色を「補って」描いている。** これが視覚予測誤差の増加（9.6 → 14.4、+49%）の主な中身と考えられる（確認はしていない）。
5. 他者側は自己側より変化が大きい：h²→他者 0.959 → 0.865（A0 の回帰器では 0.767）、Fig.5 の other_other 0.058 → 0.108（マージン 0.091 → 0.052）。他者側 Encoder の出力 ov_enc は入れ替えで大きく変わる（対の距離比 1.10）。ただし自他の向き（other_other < other_self）は保たれる。

**解釈（主張の範囲）**
- 指導教員の指摘「今のモデルでは価値が位置に結びついている」は、critic の段階で確認された。critic は報酬が色で定義されていても、学習データの中で色と場所が分けられていなかったため、場所（見え方の配置）で価値を出している。v7 で最良方向が場所によらずほぼ一定だったこと（§5.8）とも整合する。
- 共有モジュールの自己表現（h¹）が入れ替えでほぼ変わらないのは、入力（probe-Q と sv_enc）がほぼ変わらないためで、共有モジュールが色を無視することを学んだという証拠ではない。

**限界**
- critic・actor の地図は、相手を (0,0) に置いた 1 フレームの評価（v6 と同じ）。
- §3.5 の Encoder の診断は事前登録していない探索的なもので、viz20 の 2020 フレーム対に基づく。
- v5_base_l1 は単一シード。

**段階Bの設計に関わる懸念（提案は報告で行い、ここでは記録のみ）**
- **B3 は Encoder・Decoder を凍結する（R3-A_400 と同じ）。** 凍結 Encoder の出力は赤・緑の区別をわずかにしか持たず、凍結 Decoder は列の位置から元の配色を描く。このため、B3 では (a) 色の情報は主に B1 の critic の probe-Q から入ることになり、(b) 入れ替えのエピソードの予測画像は、共有モジュールが何を学んでも元の配色のままになる可能性が高い。
- **B4 の主関門1の比較相手（R3-A_400）について**：凍結 Encoder の出力から配置が 1 フレームで 0.879 読めるので、R3-A_400 の h¹ からも配置がある程度読める可能性がある（未測定）。その場合、「R3-A_400 より 0.15 以上高い」は、色に結びついた価値の効果だけを見ていることになる（基準として妥当だが、0.80 に届くかどうかは R3-A_400 の水準次第）。

- B3-frozen と B3-ft を 3 シードずつ並行（GPU1〜6、6 本）なら、壁時計は長い方の B3-ft で決まり **約 25〜30 h**（6 本同居で 1〜2 割遅くなる可能性あり）。GPU7 は評価・B3-pre の (1) に使える。中間の評価用 `saved.h5`（1 本 約 0.7 GB、grid は 6.7 GB）は都度削除。空き 140 GB に対して十分。

- **決めていただきたい点**：
  - B3-ft：学習し直す範囲。案：`vision_encoder_module`・`share_lns`・`vision_decoder_module` を凍結から外し、`integration_module`・`feature_prediction_module` は凍結のまま。Encoder の weight decay は exp1 と同じ 1e-3。損失は R3-A と同じ L1。
  - B3-ft・B3-pre の Fig.5 の Decoder の学習データ：元の Autoencoder は元の配置だけのデータ（`self_random_other_stay_1000`）で学習している。同じデータで学習し直すと、Decoder が再び「列の位置から元の配色を描く」可能性が高い。案：`v10_swapmix_r2` の train の先頭 1000 エピソード（元と同じ規模、両配置を含む）。
  - B3-pre の「1000ep」：元論文の `exp1_*_1000` の「1000」は**エピソード数（データの規模）**で、エポック数は 200（MSE）＋ 200（L1、Decoder のみ）。`v10_swapmix_r2` の train 3000 エピソードを全部使うか、先頭 1000 エピソード（元論文と同じ規模）にするか。また元論文の Encoder の学習データは A-2 が静止（`self_random_other_stay`）だが、`v10_swapmix_r2` では A-2 が動く。
